# 试卷宝 v2 — 项目重启规划与分阶段实施方案

> 版本：v1.0 | 日期：2026-05-31 | 作者：Hermes（基于旧项目全部文档的系统性分析）
> 前提：旧项目 `exam-paper-tool` 已有丰富的研究积累（技术路线对比、风险分析、50张样本分类、V0实验方案），但仓库结构混乱，决定重启。

---

## 零、为什么要重启

旧项目 `exam-paper-tool` 不是"没有内容"——恰恰相反，内容是充足的。问题在于：

| 旧项目的问题 | 表现 |
|-------------|------|
| 文档散落 | 同一份"功能方案框架"同时出现在 `00_项目总览/`、`research/001_功能方案/`、`99_归档/` 三个位置 |
| 目录混乱 | `02_V0擦除实验/` 和 `06_实验与样本/03_擦除实验/` 两套目录做同一件事 |
| 命名不一致 | 有的叫"试卷宝"，有的叫"exam-paper-tool"，有的叫"试卷扫描实验" |
| 版本漂移 | README 说 Phase 0，项目总览说 V0，实验报告说 Phase 1C——读者不知道当前到底在哪一步 |
| 实际进度的错觉 | 文档很多，但实际擦除 0 张——给人一种"做了很多"的错觉 |

**重启的目的不是否定过去的工作，而是用更清晰的骨架重新组织，让每个阶段有明确的入口、产出和验收标准。**

---

## 一、项目一句话定义

**把做过的卷子变回空白卷子。** 家庭学习场景：拍照 → 擦手写 → 输出可重新打印的干净试卷。

**核心约束：** 全本地、不上传云端、不依赖 GPU、非技术人员可用。

---

## 二、为什么用这个阶段拆分

### 设计原则

```
每个阶段必须同时满足三个条件：
  ① 有明确的可验证产出（不是"研究了什么"，而是"产出了什么能用的东西"）
  ② 不依赖尚未验证的技术（下一阶段的技术基础必须在本阶段验证通过）
  ③ 即使后续阶段不做，当前阶段也有独立的家庭学习价值
```

### 为什么是 5 个阶段而不是 3 个或 8 个

| 如果只有 3 个阶段 | 问题 |
|------------------|------|
| 研究→开发→上线 | "开发"太庞大，中间没有检查点，容易失控 |

| 如果分成 8 个阶段 | 问题 |
|------------------|------|
| 过度拆分 | 每个阶段产出太薄，缺乏成就感，管理成本高 |

**5 个阶段的粒度**：
- Phase 0 验证**能不能做**（技术可行性，不写一行产品代码）
- Phase 1 做出**能用的东西**（命令行工具，自己能跑通）
- Phase 2 做出**别人也能用的东西**（有界面，家庭成员能用）
- Phase 3 从"擦除工具"变成**学习工具**（错题管理，有积累价值）
- Phase 4 从"学习工具"变成**智能助手**（自动化 + 学习闭环）

每个阶段跨一个"价值台阶"，不多不少。

## 三、五阶段总览

```
Phase 0     Phase 1       Phase 2        Phase 3        Phase 4
验证可行性   CLI 工具      GUI 工具       错题管理       智能升级
  ↓           ↓             ↓              ↓              ↓
能不能擦？   能擦了         能给别人用了    能积累错题了    能自动了
 2天         1周           2周            3周            远期
```

## 四、各阶段详细计划

### Phase 0：可行性验证（2天）

**一句话目标**：用 5 张真实样本，验证"人工框选 + 颜色阈值 + 涂白/inpainting"能不能擦干净手写。

**为什么必须先做这一步**：
- 这是整个项目的**技术地基**。如果这一步失败了（比如 5 张样本全部效果差），说明半自动路线走不通，需要推翻重来——那后面四个阶段都不用做了
- 投入极小（2天），损失可控。比起花 2 个月做完 GUI 才发现效果不行，这 2 天是必须的

**产出**：
| 文件 | 内容 |
|------|------|
| `experiments/v0/report.md` | 5 张样本的擦除效果评分 + 对比图 |
| `experiments/v0/conclusion.md` | 能处理/不能处理的图片类型清单 + 是否进入 Phase 1 的判断 |

**验收标准**：≥3 张样本达到"可打印重练"水平（7/10分），0 张出现题干/公式/图形被破坏。

**从旧项目迁移**：
- `02_V0擦除实验/试卷宝V0擦除实验执行方案.md`（5 张样本任务卡，坐标格式，评分标准）

---

### Phase 1：CLI 命令行工具（1周）

**一句话目标**：做出一个可以在终端里跑的命令行擦除工具，自己能用来处理任意试卷图片。

**为什么做成 CLI 而不是直接做 GUI**：
- CLI 是**最快的验证方式**——不需要写 UI 代码，一个 `python eraser.py input.jpg --color blue` 就能跑
- CLI 是 GUI 的**内核**。CLI 写好了，GUI 只是在外面包一层壳，不会出现"UI 做完了但核心功能没跑通"的尴尬
- CLI 天然适合**批量处理**，为 Phase 3 积累数据

**产出**：
| 文件 | 内容 |
|------|------|
| `src/eraser.py` | 主程序：图片加载 → 预处理 → mask 生成 → 填充 → 输出 |
| `src/preprocess.py` | 透视矫正 + 去噪 + 对比度增强 |
| `src/mask.py` | HSV 颜色阈值 mask 生成（蓝/红/黑三种模式） |
| `src/fill.py` | 白色填充 + INPAINT_TELEA + INPAINT_NS 三种模式 |
| `tests/` | 5 张标准测试样本 + 预期输出 |
| `README.md` | 安装 + 使用说明 |

**验收标准**：处理 10 张全新试卷图片，蓝笔和红笔场景擦除成功率 ≥ 70%。

**项目结构（Phase 1 完成时）**：
```
exam-paper-tool/
├── README.md                # 项目说明
├── docs/
│   ├── plan.md              # 本文件（阶段规划）
│   └── architecture.md      # 技术架构说明
├── experiments/
│   └── v0/                  # Phase 0 实验记录
├── src/
│   ├── eraser.py            # 主入口
│   ├── preprocess.py        # 预处理
│   ├── mask.py              # mask 生成
│   └── fill.py              # 填充算法
├── samples/                 # 测试样本（只放脱敏后的）
├── tests/                   # 测试脚本+预期输出
└── requirements.txt
```

**从旧项目迁移**：
- `06_实验与样本/03_擦除实验/脚本草稿/erase_handwriting_path_a.py`（108 行脚本草稿，可作为 `mask.py` 的起点）
- 50 张样本中的"可擦除"22 张（作为测试素材，需要脱敏）

---

### Phase 2：GUI 桌面工具（2周）

**一句话目标**：做出家庭成员（非技术人员）可以打开的桌面应用，鼠标框选擦除区域，一键输出干净试卷。

**为什么用 tkinter 而不是网页**：
- tkinter 是 Python 内置库，零额外依赖
- 不需要启动服务器、不需要浏览器、不需要网络
- 家庭场景：打开一个应用比"打开浏览器访问 localhost:5000"更自然
- 如果以后想做网页版，Phase 1 的 CLI 核心代码不用改，只换 UI 层

**产出**：
| 功能 | 说明 |
|------|------|
| 图片打开 | 支持拖拽、文件选择器 |
| 颜色选择 | 蓝笔/红笔/黑笔切换，阈值滑块实时预览 mask |
| 框选模式 | 鼠标拖拽矩形标记擦除区域 |
| 橡皮擦模式 | 从 mask 中移除误选区域 |
| 撤销/重做 | Ctrl+Z / Ctrl+Y |
| 填充方式切换 | 白色填充 / TELEA / NS |
| 对比视图 | 左右分屏：原图 vs 结果 |
| 保存 | PNG 输出，保留原始分辨率 |
| 批量模式 | 选择文件夹，一次性处理全部图片 |

**验收标准**：一个不懂命令行的家庭成员能独立完成"打开图片 → 框选 → 擦除 → 保存"全流程。

---

### Phase 3：错题管理（3周）

**一句话目标**：不只是擦除，还能把"做错的题"收集起来，生成错题重练卷。

**为什么这个阶段不能在 Phase 1 就做**：
- 错题管理的前提是 **擦除流程稳定**。如果擦除还经常出错，积累的错题数据质量就差
- 错题管理需要 **足够的样本积累**。Phase 1/2 用下来的真实数据，才能知道"错题管理"到底需要管什么
- **功能边界要清晰**：Phase 2 之前，用户只需要"擦除"这一个动作；Phase 3 引入"标记错题"这个新动作，需要先确认 Phase 2 的用户体验是顺滑的

**产出**：
| 功能 | 说明 |
|------|------|
| 错题标记 | 在 GUI 中标记"这道题做错了" |
| 题目切分 | 按题号/版面自动分割题目区域 |
| 错题收集 | 结构化存储（题目图片 + 学科 + 日期 + 错因标签） |
| 重练卷生成 | 自动排版导出 PDF/打印版 |
| 错题统计 | 按知识点/错因汇总 |

**验收标准**：家长能用它生成一份包含 10 道错题的可打印重练卷。

**从旧项目迁移**：
- 50 张样本分类数据（可擦除 22 张、适合识别 11 张、疑似错题 3 张）

---

### Phase 4：智能升级（远期，触发条件满足后启动）

**一句话目标**：从"半自动工具"升级为"大部分自动 + 少数人工确认"。

**为什么放在远期而不是现在规划太细**：
- Phase 4 依赖 Phase 0-3 积累的标注数据（每次人工框选就是一次标注）
- 触发条件：≥200 张带标注的样本
- 如果 Phase 3 就满足需求了，Phase 4 可以不启动——**不做也是一种成功**
- 现在就规划 Phase 4 的细节是过度设计

**方向**（不展开，仅列方向）：
- 训练本地小模型识别手写区域（基于积累的框选数据）
- OCR 辅助题号识别（不识别完整题目，保护公式/图形）
- 错因自动归类
- 复习计划（基于艾宾浩斯遗忘曲线）

## 五、为什么这个计划是"对的"

### 5.1 每一步都有"不做后面阶段"的自由

```
Phase 0 失败 → 项目终止，损失 2 天。不丢人，这是最负责任的结果。
Phase 1 做完 → 你自己能用。够了吗？够了就停。
Phase 2 做完 → 全家人能用。够了吗？够了就停。
Phase 3 做完 → 有学习积累价值。够了吗？够了就停。
Phase 4 启动 → 因为前三个阶段积累的数据让它变得可能。
```

每个阶段都是**独立的交付物**，不是"为了下一个阶段而存在"的过渡步骤。

### 5.2 每个阶段的验收标准是可量化的

| 阶段 | 验收标准 | 谁来判断 |
|------|---------|---------|
| Phase 0 | ≥3/5 张 7 分以上，0 张硬性失败 | 你自己的肉眼评分 |
| Phase 1 | 10 张新图 70%+ 成功率 | 脚本自动统计 |
| Phase 2 | 非技术人员能独立完成全流程 | 家庭成员实测 |
| Phase 3 | 能生成含 10 道错题的重练卷 | 你打印出来看效果 |
| Phase 4 | 触发条件（200张标注）| 数据统计 |

没有"做得更好了""体验提升了"这种模糊标准。

### 5.3 代码和文档的边界清晰

- **旧项目**的问题：`research/001_功能方案/试卷宝功能框架.md` 里面既有功能描述又有技术代码——分不清是文档还是代码
- **新项目**的规则：
  - `docs/` 目录只有纯文档（Markdown），不含代码
  - `src/` 目录只有代码，不含长篇方案论述
  - `experiments/` 目录只有实验数据和报告，不含产品代码
  - 一个文件只做一件事

### 5.4 旧项目的有价值资产不会丢

| 旧项目资产 | 迁移到新项目的位置 | 价值 |
|-----------|-------------------|------|
| 技术路线对比报告 | `docs/reference/tech-comparison.md` | Phase 0-1 的技术选型依据 |
| 风险清单与边界说明 | `docs/reference/risks.md` | 全程参考，避坑 |
| V0 实验方案 | `experiments/v0/plan.md` | Phase 0 执行手册 |
| 擦除脚本草稿 | `src/` 重构后纳入 | Phase 1 的代码起点 |
| 50 张样本分类数据 | `experiments/samples/catalog.csv` | Phase 0-3 的素材库 |
| OpenCode 技术方案 | `docs/reference/opencode-tech-proposal.md` | Phase 0-1 技术参考 |
| Hermes 需求分析 | `docs/plan.md` | → 本文件替代（升级版） |

## 六、不做什么（刻意为之）

| 不做 | 原因 |
|------|------|
| 不一开始就做用户系统 | 家庭内部用，不需要多用户 |
| 不一开始就做云端同步 | 隐私红线 |
| 不一开始就做全自动 AI | 真实试卷差异太大，全自动会悄悄出错 |
| 不一开始就引入深度学习 | 部署成本高（100MB+模型、GPU需求），不值得 |
| 不追求处理所有类型试卷 | 先处理蓝笔/红笔场景（覆盖 60%+ 真实场景） |
| 不做 OCR 重排数学题 | 数学公式 OCR 是业界公认难题，OCR 错误会改变题目内容 |
