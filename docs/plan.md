## 零、终极目标（我们要做成什么样）

### 一句话

**一个网页，上传试卷照片 → 擦除手写 → 挑出错题 → 输出干净试卷和错题集。**

### 完整流程

```
家长打开网页
    │
    ▼
上传试卷照片（手机拍照 / 微信图）
    │
    ▼
选择是谁的试卷：  K1  /  K2           ← 手工选（不追求自动识别）
选择什么学科：    数学 / 语文 / 英语 / 科学
    │
    ▼
系统自动处理：
  ┌─ 擦除手写答案、红笔批改 ──→ 输出干净试卷图
  │
  └─ 识别错题区域        ──→ 输出错题列表
    │
    ▼
结果页展示：
  ┌─ 左侧：原图 vs 干净图（并列对比）
  │
  └─ 右侧：错题列表（家长确认 / 修正）
    │
    ▼
家长确认 → 保存
  ├─ 干净试卷：可下载/打印
  └─ 错题记录：按 K1/K2 + 学科 + 日期归档
```

### 终极目标的验收标准

| # | 标准 | 怎么验证 |
|---|------|---------|
| 1 | 上传一张试卷照片，2 分钟内完成全流程（上传 → 擦除 → 错题挑出 → 保存） | 找一张真实试卷计时 |
| 2 | 擦除后印刷题干 100% 完整（0 误删） | 肉眼对比题干区 |
| 3 | 错题检出率 ≥ 80%（10 道错题至少检出 8 道） | 人工标注一批对比 |
| 4 | 非技术人员（细影）能独立完成全流程 | 给细影用一次，不问任何问题 |
| 5 | 全程不上传任何图片到云端 | 断网也能用 |

## 一、为什么这个计划更合理

### 设计铁律

```
每个阶段 = 一个独立的、可用的产品
不是"为下一个阶段搭地基"，而是"现在就能用的东西"
```

### 对比旧方案的问题

| 旧方案（v2） | 问题 | 新方案（v3） |
|-------------|------|-------------|
| Phase 0→1→2→3→4，线性排列 | 看不出终极目标长什么样 | 先画终极目标，再倒推到今天 |
| 每个阶段侧重"技术验证" | 用户看不到价值 | 每个阶段有用户可感知的产出 |
| Phase 3 才做错题 | 错题是核心需求，太晚了 | 从 Phase 2 开始就带错题 |
| 没有网页的规划 | 最终形态不清晰 | 明确最终是网页，从 Phase 2 开始就有 |

### 核心思路：从用户视角倒推

```
不是问"我们能做什么技术"然后往上堆
而是问"用户要什么体验"然后拆成最小可用版本

用户体验的最小闭环：
  上传 → 擦除 → 看到结果 → 保存
只要这个闭环通了，就有一个"能用"的产品

然后再在这个基础上：
  + 错题识别
  + 批量处理
  + 智能分类
```

## 二、五阶段总览

```
Phase 1         Phase 2          Phase 3           Phase 4          Phase 5
CLI 验证        Web 上传+擦除    错题识别          批量+归档         智能升级
 2天            1周              2周               2周              远期
  ↓              ↓                ↓                 ↓                ↓
能不能擦？      能上传能擦了      能挑错题了        能批量管理了      能自动分类了
```

### 每个阶段结束后的东西

| 阶段 | 你手里有什么 |
|------|------------|
| Phase 1 | 命令行工具，自己能用 |
| Phase 2 | 网页，上传→擦除→下载，**细影能用** |
| Phase 3 | 网页 + 错题识别 + 错题导出 |
| Phase 4 | 历史记录、批量管理、按孩子/学科归档 |
| Phase 5 | 自动识别孩子和学科（省掉手工选择） |

## 三、各阶段详细计划

### Phase 1：CLI 擦除验证（2 天）

**目标**：验证"人工框选 + 颜色阈值 + 白色填充"这套技术路线能不能擦干净手写。

**为什么必须先做这一步**：
- 这是整个项目的地基。如果这一步证明擦不干净，后面的网页、错题全都白做
- 投入极小（2 天），失败成本可控
- 这一步**不需要网页**，命令行跑通就行

**输入 → 输出**：
```
输入：一张试卷照片 JPG
  → python eraser.py exam.jpg --color blue
输出：干净试卷图 clean.jpg + 擦除区域预览图
```

**验收标准**：

| # | 标准 | 验证方法 |
|---|------|---------|
| 1 | 5 张真实样本，≥3 张达到"可打印重练"（7/10 分） | 青山肉眼评分 |
| 2 | 0 张出现题干/公式/图形被破坏 | 逐张对比原图 |
| 3 | 蓝笔和红笔场景擦除成功 | 单独验证 |

**如果失败**：
- 换 inpainting 方案（INPAINT_TELEA / NS）
- 如果还不行 → 讨论是否引入深度学习

---

### Phase 2：Web 上传 + 擦除（1 周）

**目标**：做出一个网页，可以上传图片、看到擦除结果、下载干净图片。**这是第一个"能给别人用"的版本。**

**用户流程**：
```
打开网页 → 拖拽/点击上传图片 → 选择是谁(K1/K2) + 学科（下拉框）
→ 点击"开始擦除" → 看到原图 vs 干净图（并列）→ 下载干净图
```

**技术方案**：
```
前端：纯 HTML + JS（一个文件，双击打开就能用，不需要服务器）
后端：Python Flask（轻量，本地 localhost:5000）
擦除引擎：Phase 1 的核心代码直接复用
```

**界面草图**：
```
┌──────────────────────────────────────────────────────┐
│  试卷宝                                     [设置 ⚙] │
├──────────────────────────────────────────────────────┤
│                                                      │
│   ┌─────────────────────────────────────┐            │
│   │        拖拽图片到这里                  │            │
│   │        或点击上传                     │            │
│   └─────────────────────────────────────┘            │
│                                                      │
│   孩子：[K1 ▼]   学科：[数学 ▼]   笔色：[蓝色 ▼]      │
│                                                      │
│              [ 开始擦除 ]                             │
│                                                      │
│   ┌──────────────┐  ┌──────────────┐                 │
│   │   原图        │  │   干净图      │                 │
│   │              │  │              │                 │
│   │              │  │              │                 │
│   └──────────────┘  └──────────────┘                 │
│                                                      │
│              [ 下载干净图 ]                           │
└──────────────────────────────────────────────────────┘
```

**验收标准**：

| # | 标准 | 验证方法 |
|---|------|---------|
| 1 | 上传一张图片 → 10 秒内看到擦除结果 | 计时 |
| 2 | 干净图可以下载 | 下载后打开看 |
| 3 | 细影能独立完成完整流程 | 不给任何指导，让她试一次 |
| 4 | 蓝笔和红笔场景都能处理 | 各测试 3 张 |

---

### Phase 3：错题识别 + 导出（2 周）

**目标**：系统能自动标记"哪些区域可能是错题"，家长确认后，导出错题集。

**为什么不在 Phase 2 就做**：
- Phase 2 的目标是"擦除能跑通"。如果擦除还不稳定，识别错题没有意义
- 错题识别需要额外的技术（红笔区域检测 = 批改痕迹 = 错题信号），需要先验证

**错题识别逻辑**：
```
红笔区域 → 大概率是批改标记 → 标记为"疑似错题"
家长确认 → 框选/调整错题区域 → 确认
```

**导出格式**：
```
错题集 Markdown:
  # K1 数学错题 2026-05-31
  ## 第3题（分数运算）
  [错题图片]
  错因：计算错误
  
  ## 第7题（几何）
  [错题图片]
  错因：辅助线画错
```

**验收标准**：

| # | 标准 | 验证方法 |
|---|------|---------|
| 1 | 红笔批改区域 100% 被标记 | 找 5 张有红笔批改的试卷 |
| 2 | 错题检出率 ≥ 80% | 人工标注 10 道错题，看检出几道 |
| 3 | 能导出 Markdown 错题集 | 打开看格式是否正确 |
| 4 | 家长可以在网页上增删错题 | 点几下试试 |

---

### Phase 4：批量管理 + 归档（2 周）

**目标**：不只是"一张一张处理"，而是能管理所有历史试卷和错题。

**新增功能**：
```
历史记录页：
  ┌─ 按孩子筛选：K1 | K2 | 全部
  ├─ 按学科筛选：数学 | 语文 | 英语 | 科学
  ├─ 按日期排序
  └─ 每条记录：原图缩略图 + 干净图 + 错题数 + 日期

错题复习：
  ┌─ 选择孩子 + 学科 + 时间范围
  ├─ 自动合并所有错题 → 生成"错题重练卷"PDF
  └─ 一键打印
```

**验收标准**：

| # | 标准 |
|---|------|
| 1 | 能看到所有历史处理记录 |
| 2 | 能按 K1/K2 和学科筛选 |
| 3 | 能生成并打印错题重练卷 |

---

### Phase 5：智能升级（远期，按需启动）

**目标**：省掉"手工选择孩子和学科"这一步。

**注意**：这是锦上添花，不是核心功能。如果 Phase 4 已经够用，Phase 5 可以不启动。

**方向**（当前不展开）：
- 用简单规则识别学科（数学 = 有公式符号，语文 = 大段文字，英语 = 字母为主）
- 用照片元数据（谁手机拍的）推测是 K1 还是 K2
- 如果识别不准，保留手工选择作为后备

**触发条件**：手选累积了 100+ 条记录，有足够数据训练/调参。

## 四、技术选型总表

| 层级 | Phase 1 | Phase 2 | Phase 3-4 | Phase 5 |
|------|---------|---------|-----------|---------|
| **擦除引擎** | Pillow + OpenCV | 同 Phase 1 | 同 Phase 1 | 同 Phase 1 |
| **前端** | 无（CLI） | HTML + JS（单文件） | Flask + 模板 | 同 Phase 4 |
| **后端** | 无（脚本） | Flask（轻量） | Flask | Flask |
| **存储** | 文件系统 | 文件系统 + JSON | SQLite | SQLite |
| **部署** | 终端 | `python app.py` | 同 | 同 |

**设计选择**：
- 全程不引入 React / Vue / Next.js，不用数据库服务器，不用 Docker
- 原因：这是**家庭工具**，不是 SaaS 产品。一个 `python app.py` 就能跑的东西，不应该需要 `docker compose up -d postgres redis minio`

## 五、和旧方案的对比

| 维度 | 旧方案 v2 | 新方案 v3 | 为什么改 |
|------|----------|----------|---------|
| Phase 顺序 | 技术验证→CLI→GUI→错题→智能 | CLI→Web+擦除→错题→归档→智能 | Web 提前到 Phase 2，让用户更早看到可用产品 |
| 错题优先级 | Phase 3 才做 | Phase 3 做（但 Phase 2 就为错题留接口） | 错题是核心需求，不能太晚 |
| 终极目标 | 模糊（"学习工具"） | 明确：网页上传+擦除+错题 | 先画终点再倒推 |
| 验收标准 | 技术指标为主 | 用户体验为主（细影能独立使用） | 工具是给人用的，不是给开发者用的 |
